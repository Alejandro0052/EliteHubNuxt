- (capability) CAP-1 Registration & Type-Segmented Onboarding (FR-1-6, FR-38): user selects exactly one TipoUsuario at registration with type-specific fields and mandatory T&C; type locked permanently, no self-service or admin change path
- (capability) CAP-2 Content Editor Fix & Static Page Editing (FR-7-9): ContentEditor modal usable everywhere mounted; wired onto terms/privacity/aboutUs; removed from contactUs/deportistas/marcas/nutricionistas/patrocinadores
- (capability) CAP-3 Contact Form Persistence (FR-10-11, FR-41-42): anonymous contact submissions persist as Mensaje de Contacto records with Asunto and fields captured; confirmation message shown; admin has a most-recent-first inbox view
- (capability) CAP-4 Homepage Real-Time Stats (FR-12): homepage counters are live DB-computed counts per TipoUsuario plus Eventos, sharing one aggregate query with Reportes/Indicadores so figures never diverge
- (capability) CAP-5 Open Eventos/Noticias Creation (FR-13-14): any authenticated Usuario can create Eventos/Noticias; author or admin can edit/delete; non-author non-admin rejected
- (capability) CAP-6 Per-Type Directory & Profile System (FR-15-18, FR-40): four segmented infinite-scroll directories with click-through detail; self-only profile edit with admin override; deactivated accounts content hidden not deleted from public views, restored on reactivation
- (capability) CAP-7 Deportista Sport Filters (FR-19): Deportistas directory filterable by the fixed Deporte list; no filter shows all
- (capability) CAP-8 Marca Product/Service Catalog (FR-20-23, FR-39, FR-43): only Marca accounts create contact-only Items de Catalogo shown on own profile and in an aggregate category-browsable Catalogo view; no payment; author-or-admin edit/delete
- (capability) CAP-9 Nutricionista Ratings & Reviews (FR-24-25, FR-36-37): authenticated Usuario leaves at most one rating+comment Resena per Nutricionista, shown alongside especialidad; admin can retract reviews and block authors
- (capability) CAP-10 Publicaciones / Home Feed (FR-26-28): any authenticated Usuario posts text+optional image to a shared most-recent-first feed; author edits/deletes own post, admin deletes any
- (capability) CAP-11 Reportes/Indicadores (FR-29-30): admin dashboard shows donut/bar chart plus numeric counts of Usuarios by TipoUsuario, sharing the FR-12 aggregate so totals match the homepage
- (capability) CAP-12 Settings & Theme Toggle (FR-31-32): Usuario toggles light/dark theme from Settings, persisted across sessions, alongside existing content-policy edit entry points
- (capability) CAP-13 Visual/UI Overhaul (FR-33-34): visual refresh (not rebrand) across directories/detail views, eventos/noticias listing, admin panel, login/register (drop placeholder Jugador.jpeg), sitewide card hover micro-interaction; responsiveness preserved everywhere as a hard gate
- (capability) CAP-14 File Storage Migration (FR-35): uploaded files move off local disk to persistent non-local storage; app fully functional after restart/redeploy with no local-disk state retained
- (constraint) Platform is web-only, responsive Nuxt 4, no native mobile app; every new/modified surface must preserve current responsive behavior across breakpoints (FR-34) as a release gate
- (constraint) No anonymous/public visibility: directories, profiles, catalogo, and feed require an authenticated account; only home/terms/contact stay public (confirmed decision, PRD SS2.2)
- (constraint) TipoUsuario is immutable after registration, enforced server-side per ARCHITECTURE-SPINE AD-8 via Usuario-Informacion-TipoUsuario (no direct relation); no self-service or admin write path may change it
- (constraint) Author-vs-admin authorization must be enforced server-side, not just UI-hidden, per ARCHITECTURE-SPINE AD-1 per-resource action-role matrix: e.g. admin deletes but cannot edit another Usuario Publicacion; admin retracts but cannot edit/delete Resenas
- (constraint) Auth freshness: activo/isAdmin rechecked from DB once per request via requireSession() per ARCHITECTURE-SPINE AD-4; JWT claims alone never trusted for these two fields
- (constraint) Deactivated-user content cascade uses shared activeUserFilter() (ARCHITECTURE-SPINE AD-5) across directories/feed/catalogo/eventos-noticias listings; Resenas are explicitly excluded from this cascade for MVP, matching PRD SS11 deferral
- (constraint) Full profile field set including health-adjacent fields (lesiones, peso, altura) and PII (fecha de nacimiento) is visible to any authenticated viewer on detail views; no field-level privacy control exists in MVP, a deliberate scope cut
- (constraint) Cost guardrail: no paid infrastructure assumed, free/open-source-tier choices only, realized as Cloudflare R2 (ARCHITECTURE-SPINE AD-2) for storage and vue-chartjs+chart.js (AD-3) for charting
- (constraint) Existing session-based auth stack (next-auth + sidebase/nuxt-auth + next-auth/prisma-adapter, layered) is retained as-is, not audited or consolidated in this MVP; next-auth pinned below 4.23.0 per ARCHITECTURE-SPINE compatibility note
- (constraint) Directory infinite-scroll must stay responsive as Usuario count grows; realized via cursor-based pagination, 20 records per batch, one fixed default per ARCHITECTURE-SPINE Consistency Conventions
- (constraint) File uploads must not silently fail or corrupt existing records; known gap of no transactional writes for compound file-upload+DB-write is explicitly carried to post-MVP maintenance, not fixed in this MVP
- (constraint) Upload/insert ordering convention: insert DB row first with null/placeholder image field, then upload, then patch row with resulting URL(s), per ARCHITECTURE-SPINE Consistency Conventions - cheapest failure mode to detect
- (constraint) Fixed-value lists (deporte, genero, pais, catalogo categories) defined once in a single shared source per ARCHITECTURE-SPINE Consistency Conventions, never hardcoded per-component
- (decision) Non-goals (PRD SS8, lifted directly): payments of any kind; legacy-account backfill/migration; PQRS complaints support; email-based password recovery; dynamic scheduling/agendas for nutricionistas; app rebrand; formal unit/component test suite and CI/CD pipeline (E2E excluded, in scope per SS9.3); RBAC activation; auth package consolidation; transactional writes for compound file-upload+DB-write operations
- (decision) Superseded non-goal: PRD SS8 listed Prisma client consistency for content/[page].* as deferred to post-MVP; ARCHITECTURE-SPINE Consistency Conventions and Structural Seed fold this exact fix into SS5.2 Content Editor Fix work (switch to shared prisma singleton) - architecture supersedes the PRD deferral for this file; not carried forward as a live non-goal
- (decision) Success signal (PRD SS10 synthesis): 100% Must-tier FRs demonstrable by 2026-08-08 and 100% Should-tier FRs demonstrable by 2026-08-22, with homepage and Reportes/Indicadores counts never visibly diverging (shared aggregate) as the standing consistency signal; counter-metrics guard against gaming completion by cutting required registration fields or skipping author/admin moderation checks
